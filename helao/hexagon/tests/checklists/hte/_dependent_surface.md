# hte dependent-surface inventory (spec §8.3(3))

Four-part inventory of what the hte experiment/sequence libraries and
station configs depend on, generated by direct grep/AST of the tracked
`helao/deploy/hte/**` source. This is the gate input that keeps the P3 wave
from repeating the old attempt's **AVOID #8** failure: experiments/sequences
libraries were left out of the wave plan until a mid-flight "Wave 3.5
emergency" forced them back in.

**AVOID #8 — explicit line:** the `helao/deploy/hte/experiments/*.py` (13
modules) and `helao/deploy/hte/sequences/*.py` (14 modules) libraries are
**in the P3c wave plan from day one**. They are not an afterthought bolted
on after the action-server ports (P3b) land; the P3 decomposition doc's
dependency order must schedule P3c as a first-class sub-project, not a
late patch.

**Reproducibility note:** the same `conda run -n helao python - <<'PY' ...`
stdin-heredoc pattern from the plan silently produced no output in this
environment (see `_member_surface.md` for the same finding). The script
below is unmodified in substance; it was run from a temp `.py` file
(`conda run -n helao python3 /tmp/p3pre_dependent_surface.py`) instead.

**Redaction note:** one raw grep hit named a private nested-deployment
repository directly in an import path. Per repo convention (nested
deployment repos under `helao/deploy/*` other than `hte`/`test`/`hexagon`
are separate, private git repositories and must never be named in the
public parent repo's docs/code), that hit is redacted below to
`helao.deploy.<private-deployment>.scripts.common.helao_nbio` — the finding
itself (a cross-deployment import exists) is preserved; the deployment name
is not.

**Script fix note (part c/d only):** the plan's part (c)/(d) script regexes
`fast:`/`bokeh:`/`bokeh_port:` directly against the raw file text, which
does not skip commented-out lines. Several hte configs carry large
commented-out blocks (scratch/history — e.g. `eche4.yml` has only 2 live
`fast:` entries but 9 more commented out; `power_supply_test.yml` has only
2 live vs. 10 commented). Regexing the raw text over-reports servers that
are not actually part of the live config. Fixed minimally by stripping
full-line comments (`ln.strip().startswith("#")`) before matching; the
corrected script and its real output are below. This is a real, load-bearing
correction — the uncorrected numbers would have told P3e to expect adapters
for servers several configs don't actually wire up.

Part (a) below uses the plan's script verbatim (unaffected by the comment
bug — import lines are never prefixed with `#` in valid Python and the
regex requires `from`/`import` immediately after leading whitespace). Parts
(c)/(d) use the corrected, comment-stripping version documented in that
section (see "Script fix note" above).

Script (verbatim logic from the plan):

```python
import re
from pathlib import Path

# (a) exp/seq library imports (what the libraries import from helao.*)
for root in ["experiments", "sequences"]:
    p = Path("helao/deploy/hte") / root
    for f in sorted(p.glob("*.py")):
        imps = re.findall(r"^\s*(?:from|import)\s+([\w\.]+)", f.read_text(), re.M)
        helao = sorted({i for i in imps if i.startswith("helao")})
        print(f"[{root}] {f.name}: {helao}")

# (c) config references to shared/action modules + (d) bokeh_port claims
cfgs = Path("helao/deploy/hte/configs")
for f in sorted(cfgs.glob("*.yml")):
    t = f.read_text()
    fasts = sorted(set(re.findall(r"fast:\s*(\S+)", t)))
    bokehs = sorted(set(re.findall(r"bokeh:\s*(\S+)", t)))
    bports = re.findall(r"bokeh_port:\s*(\d+)", t)
    print(f"{f.name}: fast={fasts} bokeh={bokehs} bokeh_port={bports}")
```

### Observations

- Every exp/seq module imports `helao.helpers.lib_decorators` and
  `helao.helpers.premodels` — the two universal dependencies of the
  Library port (the decorator machinery that registers functions into the
  flat name-keyed dict, plus the `Experiment`/`Sequence` premodel builders).
  Any hexagon Library port replacement must supply equivalents for both.
- Several experiment modules import concrete legacy driver enum/class
  modules directly (`helao.deploy.hte.drivers.motion.galil_motion_driver`,
  `helao.deploy.hte.drivers.robot.pal_driver`, `helao.deploy.hte.drivers.io.enum`,
  `helao.deploy.hte.drivers.motion.enum`, `helao.deploy.hte.drivers.spec.enum`)
  — these are param-typing/enum imports, not driver instantiation, but they
  mean the hexagon hardware-adapter port (P3a) must keep these
  driver-module import paths stable (or the exp libraries need updating in
  lockstep — a P3c/P3a coupling to track explicitly).
- `CLAD_exp.py` imports `helao.deploy.hte.experiments.ADSS_exp` directly
  (intra-library cross-import) — a same-deployment coupling, not a
  cross-deployment one.
- **`UVIS_R_seq.py` imports from a private deployment's `scripts.common`
  module** (redacted above) — this is a genuine cross-deployment dependency:
  an hte sequence library function imports code that lives in a separate,
  private git repository. This is exactly the kind of dependency the old
  attempt's Wave 3.5 emergency missed. The P3c wave plan must explicitly
  handle: (1) whether this import is optional/lazy (try/except) or hard,
  (2) whether the private deployment repo is even checked out in every
  hexagon-wave dev environment, and (3) a fallback/skip path if not.

## (b) active.\*/base.\* member usage (cross-ref to Task 3 `_member_surface.md`)

import-surface + flat-namespace-collision risk (§4.3.12), not
Base/Active-member risk** — the two risk classes are disjoint and both
must be gated (this file + Task 5's collision scan).

## (d) `bokeh_port` claims (the "invisible port" hazard)

10 of 21 configs declare an explicit `bokeh_port: 5003` (the operator's
Bokeh port): `adss.yml`, `adss3.yml`, `anec.yml`, `clad.yml`, `eche10.yml`,
`eche6.yml`, `eche7.yml`, `eche8.yml`, `hispec.yml`, `uvis.yml`. The
remaining 11 declare none (`bokeh_port=[]`) — meaning those groups either
don't host an operator Bokeh app on a fixed port or rely on a
config-implicit default elsewhere.

Every config that lists `standalone_operator` under `bokeh:` but has an
empty `bokeh_port` list is the "invisible port" hazard called out in the
plan: the port is not statically visible in this config file and must be
resolved at composition time (P3e) rather than assumed absent.

Configs with a `standalone_operator` bokeh app **and no explicit
`bokeh_port`**: `ccsi1.yml`, `ccsi2.yml`, `eche4.yml`, `eche5.yml`,
`ecms1.yml`, `ecms2.yml`, `icpm1.yml`, `partialccsi1.yml`,
`power_supply_test.yml`, `xrfs1.yml` — **10 configs**. (`gamry.yml` has no
`standalone_operator` bokeh app at all, so it is not part of this hazard
set.) These 10 configs are the concrete "invisible port" instances P3e must
resolve explicitly (find the actual bound port via each server's own
`host`/`port` keys, not assume a missing `bokeh_port` means no operator
UI).
