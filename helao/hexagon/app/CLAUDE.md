# helao/hexagon/app — dispatch loop and host traps

<!-- Split out of the root CLAUDE.md. Loaded when work touches this directory. -->

**`start_condition` is only honoured because the dispatch loop's history poll releases on *acknowledgement*, not on completion.** After every dispatch the loop waits for the dispatched uuid to appear in `orch.action_history` (`orch_effects.py`'s `DispatchHeadAction`, the only copy) so the next action's condition reads current status. `action_history` is written by `update_status`, and from 2026-03-19 to 2026-09-11 that only registered a uuid found in an endpoint's `nonactive_dict` — a *terminal* status. The poll therefore waited for each action to **finish**: every action ran serially, `no_wait` could never overlap anything, and nothing anywhere reported a fault. `ingestion.py` now also registers from `active_dict`. `helao/hexagon/tests/test_no_wait_overlap_live.py` is the gate: a blocking ORCH `wait` with a `no_wait` SIM acquisition under it must be simultaneously active on a real group.

Two further traps in that area. **`orch.last_action_uuid` is a `str`** (the dispatch response is `as_dict`-serialised) while `globalstatusmodel.active_dict` is keyed by `UUID`, so `wait_for_previous`'s membership test silently never matched and that condition never waited; compare as strings. And **`loop_state == stopped` is not "parked"** — the reducer applies its state delta before running the exiting iterate's commands, so `stopped` is published while `finish_active_experiment` is still inside `orch_wait_for_all_actions` and the `clear_nonblocking` drain. A test (or a UI) that treats `stopped` as the end of a run is reading a loop that has merely stopped *dispatching*; the close-out finishing is `active_experiment is None`. Before the poll fix the loop could not get ahead of its own actions, so the two were a second apart and the distinction never showed.

**A host is the FastAPI app, so `exception_handler` is a name it must not use.** Legacy `Base`/`Orch` were plain classes *held* by the app, and their `myinit` installed an asyncio loop exception handler with `aloop.set_exception_handler(self.exception_handler)`. `ActionHost` is the app, where Starlette already owns that name as the decorator that registers HTTP handlers — so the port is `ActionHost._loop_exception_handler`, installed where `self.aloop` is captured. It matters because HELAO fires a lot of work with `create_task` and never awaits it (`move_dir` on both finalize paths, the monitors, the dispatch loop): without it the traceback goes to asyncio's default handler, whose `asyncio` logger has no HELAO handler, since `make_logger` binds handlers to a *named* logger with `propagate = False` and never to the root. The failure was invisible in the server's own log and to alerting. `hasattr(host, "exception_handler")` is **not** a check for this — it is True on every host, because that is Starlette's method.

**The head action is popped *before* its start condition is waited on, so a stop has to put it back.** `_launch_action` does `action_dq.popleft()` and only then calls `_wait_for_start_condition`, which parks on `wait_for_endpoint`/`wait_for_server`/`wait_for_orch`/`wait_for_previous`. For the whole of that wait the action exists only as a local, and `wait_for_interrupt(pending_action=A)` is what re-inserts it at the front and answers `False` so the caller bails. That parameter has existed since 2022 and **no production caller ever passed it** — only the dispatch golden master did, which is why the branch looked covered while being unreachable. A `/stop` arriving mid-wait therefore ran the action anyway once its condition came true: one more CV or pump move after the operator asked it to stop. E-stop was never affected — `_dispatch_action_locked` re-checks `loop_intent == estop or loop_state == estopped` inside the `aiolock` and refuses, and that in-lock guard covers estop *only*; plain `LoopIntent.stop` passes straight through it.

Two things to know before touching this. **The window is narrow and easy to miss in a test**: stop too early and `pre_dispatch_intent_step` fires at the intent gate *before* `popleft()`, so the action is never popped and the re-queue is never exercised — a test written that way passes against the broken code. The real condition is "the blocking action is active *and* `action_dq` is empty" (`helao/hexagon/tests/test_stop_requeues_pending_action_live.py`). And **the bail-out returns without dispatching**, so the history poll after it must skip a `last_dispatched_action_uuid` of `None` or it spins forever on the very first action of a run.

**`orch.parked_head_action` covers the wait only, so a shutdown export keeps a head parked on its start condition (`export_queues` writes it at the front of `act`).** It is cleared when the wait returns, and by `wait_for_interrupt` when that re-inserts the action. The window after that is still open: wait returned, then `aiolock`, the dispatch POST, and the first status that puts the action in `active_dict`. A SIGTERM there loses the action. Exporting it would not be safe either: `_stage_action_for_dispatch` has already run `init_act`, so a re-run would reuse the staged output dir.

**An action server is idempotent on `action_uuid`, because the dispatcher can send the same action twice.** `async_action_dispatcher` probes over RPC with a 3 s timeout and re-POSTs over HTTP when it expires, while the RPC handler keeps running. `ActionAdmission` (`action_admission.py`, used by the HTTP middleware and `rpc_dispatcher.admit`) answers a repeated uuid instead of running it. A parked action keeps the caller's uuid (it used to get a fresh one, which defeated the check). A repeat of a *running* action waits for the original handler and returns its result, so the orchestrator still reads `to_global_params` and `error_code` from it; if the original failed, the repeat fails (HTTP 500 / RPC error). An RPC *handler* error (`RPCHandlerError`) is returned as `ErrorCodes.http` and never falls back to HTTP, which would run the handler twice; only a timeout, a transport error, an unregistered route or an argument-binding failure (`handler_error=False`: the handler body never started) does. **A re-send of an errored or estopped uuid re-runs; a successful one never does.** After a dispatch error the orchestrator pauses and re-queues the *same* action (`orch_dispatch.py`), so on resume the same uuid arrives again. `admit` treats it as a fresh run when the held record is errored/estopped or its handler raised (`forget` marks the seen entry failed), and `_drop` removes the stale `actives`/`history`/seen entries so the retry's is the only record, and a live session the failed run left in `actives` with no running executor is stopped first (`set_estop`, `stop_action_task`, data logger cancelled); the finalizer pops `actives` only if the entry is its own session, so a stale session finishing late cannot remove the re-run. **A failed attempt whose executor is still running is not replaced:** it would finish later into the same output directory (finalizer writes, status, journal), under the re-run's uuid. `admit` stops it (`set_estop`, `stop_action_task`) and answers `ActionFailed` (500, "previous attempt still stopping"); the orchestrator stays paused and its next resume finds the finished record and re-runs. "Running" means registered in `host.executors`, so a session still in `_pre_exec`, or one that has popped its executor and is inside `finish()`, is dropped and re-run; that window is milliseconds and is accepted, since treating any unfinished session as live would refuse forever a session that opened but never got an executor. **The dispatcher's own copies are not a resume and never re-run:** each `async_action_dispatcher` call makes one `dispatch_id` (uuid4) and puts it on both its RPC request (`RPCRequest.dispatch_id`, omitted when None) and its HTTP re-send (`X-Helao-Dispatch-Id`). The seen entry keeps every id that reached the uuid (carried across a re-run); a failed record re-runs only for a request whose id is new, and a request whose id was already seen answers `ActionFailed` whichever copy arrives first. A never-seen uuid still runs. A queued relaunch is a fresh dispatch with its own id; estop fan-out ids are per call and unused. Answering a copy from the old record would silently skip the step. **Rollout:** update the orchestrator and the action-server hosts together. An orchestrator that predates `dispatch_id` sends none, and a request with no id re-runs a failed record, so the fallback copy of a failed RPC original can run again, as it did before this check.
